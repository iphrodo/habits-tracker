## Context

У репозиторії вже є базовий Nuxt-трекер із серверною SQLite, історією, видаленням окремих завершених спроб і PWA. Мотивацію та межі MVP описано в [proposal.md](proposal.md), контракт поведінки — у чотирьох файлах `specs/*/spec.md`. Поточний редизайн замінює сад на розвиток Наруто й додає щоденну мудрість; основний пристрій — iPhone із ярликом на домашньому екрані. Авторизації немає.

## Goals / Non-Goals

**Goals:** простий моноліт із постійною базою, перевірюваний відлік часу, виразна мобільна композиція та мінімальний операційний догляд.

**Non-Goals:** універсальний рушій звичок, фонова синхронізація записів, багатокористувацька модель, складна аналітика або гарантія роботи серверних функцій без мережі.

## Decisions

### 1. Nuxt моноліт на Node.js

Використати актуальну сумісну стабільну версію Nuxt 4, Vue 3 і TypeScript, зафіксовану lockfile під час реалізації; серверні маршрути Nitro та один Node.js процес. UI працює з API того самого origin. Клієнтська оболонка без SSR персональних даних спрощує PWA-кешування та живі таймери; серверні API залишаються у Nuxt-збірці. Офіційний [Node.js deployment Nuxt](https://nuxt.com/docs/4.x/getting-started/deployment) описує серверну збірку з точкою входу `.output/server/index.mjs`.

Окремий backend додає зайві розгортання. Статичний хостинг без серверного процесу не відповідає обраній серверній SQLite. Горизонтальне масштабування для MVP не потрібне.

### 2. SQLite та невелика схема

Драйвер SQLite обрати при реалізації за сумісністю з обраною Node LTS; доступ через окремий серверний repository-шар і параметризовані SQL-запити, без обов'язкового ORM. Версійовані SQL-міграції, foreign keys, WAL і обмежений busy timeout. Файл бази та супутні WAL-файли живуть на постійному локальному volume за межами збірки й public.

Планована схема:

- `attempts`: `id`, `started_at` (UTC epoch milliseconds), `ended_at` nullable, `start_timezone` (IANA), `version`, `created_at`, `updated_at`. Частковий унікальний індекс гарантує одну активну спробу. Завершення не раніше початку; сервер перевіряє неперекриття.
- `milestone_acknowledgements`: `attempt_id`, `milestone_days`, `acknowledged_at`, унікальна пара спроба/віха. Визначає лише показ святкувань, а не саме право на досягнення.
- `mutation_receipts`: унікальний request id, тип операції, хеш payload і результат для повторюваних записів. Один id з іншим payload відхиляється. Receipt і бізнес-зміна зберігаються в одній транзакції.
- `schema_migrations`: застосовані версії міграцій.
- `daily_wisdom_reads`: `local_date` (YYYY-MM-DD), `wisdom_id` (стабільний id каталогу), `read_at` (UTC), унікальна пара дати й картки. Таблиця не посилається на attempts: нова спроба або видалення історії не стирають прочитання.

Дні й відкриті досягнення обчислюються, не записуються щохвилини. PostgreSQL створював би додаткову службу для невеликого особистого набору даних; browser storage не відповідає уточненню користувача.

### 3. Час, редагування та записи

API стану повертає активну спробу, історію, підтверджені святкування та `serverNow`. У видимій сторінці поточний час оцінюється від отриманого серверного часу й монотонного клієнтського таймера. Щохвилини перераховується UI; на focus/visibilitychange, після записів і періодично раз на п'ять хвилин виконується серверна синхронізація. За відсутності мережі знімок залишається в пам'яті з позначкою несинхронізованого стану.

`elapsed = max(0, now - startedAt)`, `days = floor(elapsed / 86400000)`. Години й хвилини — залишок, а не календарна різниця. Для історії `now` замінюється `endedAt`. Локальний ввід конвертується з явно показаним IANA-поясом; неіснуючий або неоднозначний час відхиляється з проханням обрати інший момент/явне зміщення. Сервер перевіряє відповідність моменту й поясу та майбутню дату.

Мінімальні API: `GET /api/tracker`, `POST /api/attempts` (лише перша спроба), `PATCH /api/attempts/:id` (активна спроба), `DELETE /api/attempts/:id` (лише обрана завершена спроба), `POST /api/attempts/restart`, `POST /api/milestones/acknowledge`, `GET /api/wisdom/today?timezone=<IANA>`, `POST /api/wisdom/read`. Записи передають request id; редагування й перезапуск — очікувані id/version активної спроби. HTTP 400 означає некоректне введення, 403 — сторонній origin, 409 — конфлікт стану, 503 — тимчасова недоступність сховища. Помилки не розкривають SQL або секретів.

Перезапуск транзакційно закриває стару й відкриває нову спробу в один серверний момент. Якщо відповідь загубилась, клієнт спершу перечитує стан, а повторює запит із тим самим request id. Нова спроба не створюється оптимістично. Спрощення MVP: перезапуск відбувається зараз; ретроспективне редагування завершеної історії не входить у цю версію.

### 4. Відкритий особистий трекер

Застосунок не має реєстрації, пароля, сесій чи екрана входу. Він передбачений для розгортання у приватному домені користувача; це зручніший MVP, але не ізоляція даних між людьми. `NUXT_TRUSTED_ORIGIN`, якщо заданий, захищає записи від сторонніх origin. API-відповіді лишаються `Cache-Control: no-store`, а service worker не кешує API.

Не додавати OAuth або власну авторизацію. Якщо трекер стане доступним для інших людей, потрібна окрема зміна з моделлю доступу, а не прихований пароль у клієнті.

### 5. Візуальний напрям «Шлях шинобі»

Робоча назва — «Вільно», головний екран — «Твій шлях шинобі». Одна світла тема: пергамент `#F7F0E3`, чорнильний текст `#22242C`, помаранчевий акцент `#E87524`, червоні печатки й синя чакра для декору. Контраст усіх текстових пар перевірити. Сувої, туш, рамки манґи й символіка Naruto замінюють ботанічні мотиви. Українські підписи мають пріоритет; японські змістові написи отримують перевірений переклад. Системний шрифт для основного тексту, табличні цифри 80–96 px з адаптивним зменшенням, поля 20–24 px.

«Сьогодні»: назва й рівень; центральний образ саме Наруто Узумакі та великий лічильник; години/хвилини, дата початку й прогрес до наступного рівня; нижче сувій мудрості дня та «Перечекати бажання». На малих екранах контент прокручується. Торкання персонажа через семантичну кнопку запускає коротку реакцію й показує текст етапу без зміни даних. Пауза оформлена як концентрація чакри зі збереженням добровільного виходу й незалежного відліку.

«Досягнення»: колекція десяти етапів із порогами, станами та деталями. «Налаштування»: дата початку, історія з видаленням окремого завершеного запису, інструкція встановлення та нова спроба з підтвердженням. Порожній onboarding пропонує «Почати зараз» або дату/час без екрана входу. Тексти підтримувальні, без штрафів за пропуски.

Єдиний каталог рівнів містить поріг, українську назву, японський напис із перекладом, опис та ресурс образу; пороги й назви визначені в motivational-experience/spec.md. Це ігрова шкала рангів, статусів та авторських етапів. Напрями образів: учень Академії; Наруто з пов'язкою для Геніна; командна тренувальна поза; бойова поза для Чуніна; тренування з Расенґаном для Токубецу джоніна; доросліший образ Shippuden для Джоніна; тактична поза з мотивом маски для АНБУ; образ мудреця для Санніна; плащ Хокаге для Каге; чакра Курами для Легенди Листа. Це художня прив'язка, а не твердження про отримані Наруто звання. Кожен образ помітно відрізняється позою, одягом або формою чакри; зміни кольору рамки недостатньо.

Ілюстрації — локальні оптимізовані ресурси зі спільною композицією й текстовим fallback. Поточний образ завантажується пріоритетно, інші за потреби; важке відео чи 3D не потрібні. CSS-переходи 180–300 ms, одноразова зміна образу при підвищенні; постійна пульсація лише під час паузи. Reduced motion залишає статичні образи, доступний текст сувою й текстовий таймер.

Рівень обчислюється з повних днів активної спроби, не з натискань чи прочитань. Академія не має святкування. Дев'ять ненульових віх зберігають наявні acknowledgement: одне ненав'язливе святкування найновішої, підтвердження всіх пройдених, без повтору після перезавантаження. Корекція дати перераховує рівень та образ; нова спроба починається з Академії. Після 365 днів останній образ залишається, відлік триває.

### 6. Мудрість дня та прочитання

Підготувати локальний каталог щонайменше 30 перевірених японських прислів'їв зі стабільними id, оригіналом, ромадзі, українським перекладом, мотиваційною інтерпретацією та джерелом. Джерело доступне в деталях; інтерпретація не видається за дослівний переклад чи репліку Наруто. Зовнішня генерація чи API цитат під час відкриття не потрібні.

Сервер приймає валідований поточний IANA-пояс пристрою, обчислює локальну дату зі свого часу й вибирає вислів за порядковим номером календарної дати від фіксованої епохи modulo довжина каталогу. Номер обчислюється з календарних компонентів дати, а не 24-годинних інтервалів у локальному поясі, щоб DST не пропускав картки. Каталог і порядок фіксуються для першої версії; майбутня зміна ротації має зберігати відповідність уже призначених дат. Вибір не залежить від спроби. Пояс береться з пристрою навіть до першої спроби; некоректний пояс відхиляється зі зрозумілою помилкою.

API повертає дату, пояс, картку, прочитання та serverNow. Клієнт перевіряє зміну дати щохвилини, на focus/visibilitychange й після зміни поясу. Та сама локальна дата означає ту саму картку навіть у різних поясах. Без мережі вже завантажений текст залишається з датою й позначкою несинхронізованого стану; вчорашня картка не називається сьогоднішньою. Холодний запуск зберігає загальний офлайн-контракт.

Розкриття сувою — локальна UI-дія; явне «Прочитано» записує пару local_date/wisdom_id до SQLite. Запит передає показану дату, id, IANA-пояс та request id. Сервер перевіряє відповідність дати каталогу й допускає прочитання показаної минулої картки після півночі, але відхиляє майбутню дату в переданому поясі. Повтор ідемпотентний; receipt і запис виконуються транзакційно. Печатка відображає підтверджений стан, не впливає на рівні й не видаляється разом зі спробами. Окремий журнал читання або серія щоденних відміток до MVP не входять.

### 7. PWA без офлайн-черги записів

Manifest містить `name`, `short_name`, `start_url`, `scope`, `display: standalone`, theme/background colors, іконки 192/512 px та apple-touch-icon. Safe area через `viewport-fit=cover` та `env(safe-area-inset-*)`. Apple описує [додавання вебзастосунку на домашній екран](https://support.apple.com/en-ca/guide/iphone/iphea86e5236/ios); інструкція в UI не покладається на автоматичний install prompt.

Service worker кешує лише оболонку, локальні шрифти/іконки/статичні файли; не HTML із персональними даними й не API, включно з API мудрості та прочитань. Образи Наруто кешуються як статичні ресурси за потреби. Manifest, apple-touch-icon та кольори запуску оновлюються відповідно до нового оформлення. Вибір PWA-інтеграції перевірити на сумісність з обраним Nuxt; підтримуваний модуль або прямий Workbox мають забезпечити однаковий контракт. Холодний запуск без мережі показує нейтральну оболонку. Після завантаження дані доступні в пам'яті до закриття застосунку. Новий worker активується після згоди застосувати оновлення; незбережена форма й пауза не перериваються.

Повне offline-first сховище створило б конфлікти зі SQLite та додало чергу синхронізації; для першої версії це зайва складність.

## Risks / Trade-offs

- [Втрата ephemeral-диска під час redeploy] → постійний volume, перевірка шляху бази під час старту, процедура резервування.
- [Недоступний сервер] → явні мережеві стани, збереження відкритої форми в пам'яті, повтор зі стабільним request id.
- [Особливості встановлення iOS] → ручна перевірка нової іконки, standalone-запуску та оновлення на реальному iPhone.
- [Похибка часу або timezone/DST] → UTC моменти, серверний час та граничні тести; зміна локального годинника не переписує дату.
- [Копіювання активного SQLite-файла без WAL] → узгоджений snapshot через [SQLite Online Backup API](https://www.sqlite.org/backup.html), не звичайне копіювання живого файла.
- [Надто декоративний інтерфейс] → домінантний лічильник, статичні альтернативи руху, перевірка читабельності з VoiceOver та масштабуванням.
- [Вага образів і японського оформлення] → оптимізовані локальні ресурси, завантаження за потреби, fallback і перевірка плавності на iPhone.
- [Плутанина календарного дня з тривалістю спроби] → окремі обчислення мудрості та рівня, перевірки півночі, DST, фону й зміни поясу.

## Migration Plan

1. Зберегти наявну Nuxt основу й дані; додати адитивну міграцію daily_wisdom_reads, каталог мудрості, образи та редизайн. Рівні обчислюються з наявних дат без перезапису спроб чи acknowledgement.
2. Підготувати Node.js середовище з HTTPS і постійним volume; виконати міграції до приймання запитів. Локально використовувати доступний для запису `./data/vilno.sqlite`; у production задати шлях на постійному диску й trusted origin. Конкретний провайдер не впливає на контракт і обирається перед розгортанням.
3. Перевірити відкриття без пароля, створення спроби, рівні, мудрість і прочитання, повторний запуск процесу, резервну копію та відновлення в ізольованому середовищі.
4. На iPhone перевірити Safari й встановлений застосунок, повернення з фону, мережеві помилки, safe area та нову версію service worker.
5. Перед наступними міграціями створювати узгоджену копію; мати щоденні копії поза диском застосунку з утриманням останніх 7. Для rollback повернути попередню збірку лише за сумісної схеми, інакше зупинити процес і відновити відповідну копію, явно врахувавши втрату записів після моменту копії.
